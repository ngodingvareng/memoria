# API Coding Standards

This document standardizes how code is written in `api/` — architecture, file
placement, naming, function signatures, error handling, code ordering, and
style. It extends the architecture summary in the root `CLAUDE.md` with
concrete, enforceable rules and templates. Every rule below is grounded in a
pattern already established in this codebase, or in an issue found and fixed
during a code review pass (referenced inline where relevant) — this isn't a
generic Go style guide, it's specific to how _this_ project is built.

Treat this as a living document: when a new pattern gets agreed on in review,
add it here in the same PR.

## 1. Architecture — the Dependency Rule

```
delivery/rest (handler, dto, middleware) → usecase → repository → db (sqlc-generated)
                                              ↓
                                           entity
```

Dependencies only point inward. Concretely:

- `entity` never imports anything from another internal layer.
- `usecase` imports `entity` only — never `internal/db`, never a concrete
  `internal/repository` type, never Fiber.
- `repository` implements interfaces **declared by `usecase`**, and is the only
  layer allowed to import `internal/db` (sqlc-generated). `pgtype`, `pgx`, and
  raw SQL awareness stop here — they never leak into `entity` or `usecase` as
  parameter/return types.
- `delivery/rest` (handler/dto/middleware) depends on `usecase` only, never on
  `repository` directly.
- `internal/db` is 100% generated by `sqlc` from `db/queries/*.sql` +
  `db/migrations/*.sql`. Never hand-edit it — run `just db-generate`.
- `internal/usecase/mocks` is 100% generated by Mockery. Never hand-edit — run
  `just mock-generate` after changing any interface listed in `.mockery.yaml`
  (add new interfaces there first).

**Interfaces are declared by the consumer, not the implementer** (per
`AGENTS.md`: "always implement abstractions"). A repository interface lives in
the `usecase` file of the usecase that needs it (`ThreadRepository` in
`thread_usecase.go`), not next to `threadRepository` in `internal/repository`.

## 2. Directory & File Placement

| Concern                                     | Directory                         | Filename pattern         | Example                |
| ------------------------------------------- | --------------------------------- | ------------------------ | ---------------------- |
| Domain struct                               | `internal/entity/`                | `<domain>.go`            | `thread.go`            |
| Repository interface + Input/Output structs | `internal/usecase/`               | `<domain>_usecase.go`    | `thread_usecase.go`    |
| Repository implementation                   | `internal/repository/`            | `<domain>_repository.go` | `thread_repository.go` |
| DB row ↔ entity conversion                  | `internal/repository/`            | `<domain>_mapper.go`     | `thread_mapper.go`     |
| Fiber handler                               | `internal/delivery/rest/handler/` | `<domain>_handler.go`    | `thread_handler.go`    |
| Request/response structs                    | `internal/delivery/rest/dto/`     | `<domain>_dto.go`        | `thread_dto.go`        |

Rules:

- **One file per domain per concern.** Don't merge a mapper into its repository
  file, and don't split one domain's repository across two files. This is
  deliberate even when a file ends up small (mapper files in this codebase run
  19–46 lines) — see §6 for why file-size alone isn't a reason to merge.
- **Cross-domain helpers get their own non-domain-prefixed file in the same
  package**, not duplicated per domain. Example:
  `internal/repository/pgtype_convert.go` holds `pgtype ↔ *string/*int32/...`
  conversions shared by every `*_mapper.go` — see its own header comment for the
  reasoning.
- A domain with sub-resources (e.g. `thread` → `thread_image`) gets its own full
  file set per sub-resource, not folded into the parent's files. What that
  sub-resource is _called_ is a separate question — see §3.1.
- **Packages stay flat.** `internal/entity/` is one package with one file per
  domain; no sub-packages per domain or per aggregate. This holds while the type
  count is small enough to scan.

Grouping entities into per-aggregate sub-packages (`entity/thread/`,
`entity/moment/`, making the package name the namespace and shortening
`entity.MomentImage` to `moment.Image`) is the intended escape hatch once
`internal/entity/` stops being scannable — roughly 25–30 types, or whenever
finding the right file starts costing time. It is deliberately not done now: at
~10 entities it buys nothing and costs a refactor. Two things to know before
reaching for it:

- It changes the naming rules in §3.1, since the package name absorbs the
  prefix. Choosing bare names now makes that move cheaper, not more expensive.
- Aggregates must reference each other **by ID only** (`ThreadID uuid.UUID`,
  never `*thread.Thread`). Cross-aggregate pointers create Go import cycles,
  which is the same constraint DDD arrives at independently — if a pointer feels
  necessary, the aggregate boundary is drawn in the wrong place.

## 3. Naming Conventions

| Concept                                             | Convention                                                             | Example                                                      |
| --------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| Repository/usecase interface                        | PascalCase noun/role                                                   | `ThreadRepository`, `ThreadAccessChecker`                    |
| Concrete struct implementing an interface           | unexported camelCase of the interface name                             | `threadRepository` implements `ThreadRepository`             |
| Constructor                                         | `New<Type>`, returns the interface if one exists, else `*ConcreteType` | `func NewThreadUsecase(repo ThreadRepository) ThreadUsecase` |
| Usecase operation input                             | `<Operation>Input`                                                     | `CreateThreadInput`, `UpdateThreadInput`                     |
| Usecase operation output (when not just the entity) | `<Operation>Result`                                                    | `SearchThreadsResult`                                        |
| Mapper: DB row → entity                             | `toEntity<Name>`                                                       | `toEntityThread(row db.Thread) *entity.Thread`               |
| Mapper: entity → sqlc params                        | `to<Operation><Name>Params`                                            | `toCreateThreadParams`, `toUpdateThreadParams`               |
| DTO request                                         | `<Action><Name>Request`                                                | `CreateThreadRequest`                                        |
| DTO response                                        | `<Name>Response`                                                       | `ThreadResponse`                                             |
| DTO response constructor                            | `New<Name>Response`                                                    | `dto.NewThreadResponse(e *entity.Thread) ThreadResponse`     |
| Error sentinel                                      | `Err<Reason>`, package-level `var`                                     | `errs.ErrNotFound`, `errs.ErrEmailAlreadyExists`             |

### 3.1 Entity Naming: When to Prefix With the Parent

A child entity's name is not where "belongs to a parent" gets expressed — the
foreign key already does that, and doing it twice means two places that can
disagree.

> **The foreign key expresses ownership. The name expresses identity.**

Prefix a child entity with its parent **only** when at least one of these holds:

1. **The bare noun is semantically empty.** `Image`, `History`, `Token`, `Item`,
   `Entry`, `Detail`, `Status`, `Config` mean nothing standing alone and need a
   parent to be readable at all.
2. **The bare noun is already taken** — by the language, the stdlib, a
   dependency, or another domain concept here. `Session`, `Type`, `Error`,
   `Context`, `Time` are all taken in a Go web backend.
3. **Sibling variants exist that must be told apart.** When two entities under
   different parents share a noun, both get prefixed, because the bare noun
   can't say which one it is.

If none applies, use the bare noun.

The fastest check is to say it in a sentence a domain expert would actually use.
Nobody says "add a thread-moment to the Work thread" — they say "add a moment."
When the parent doesn't appear in the spoken form, it doesn't belong in the type
name. (`OrderLine` in other codebases is not a counterexample: people really do
say "order line," because "line" alone means nothing. That's rule 1 doing the
work, not ownership.)

Applied to every entity in this codebase:

| Entity              | Verdict  | Why                                                               |
| ------------------- | -------- | ----------------------------------------------------------------- |
| `Thread`            | bare     | Root; nothing to prefix with.                                     |
| `Moment`            | bare     | "Moment" carries its own meaning — no rule applies.               |
| `Commitment`        | bare     | Same.                                                             |
| `ThreadImage`       | prefixed | Rules 1 + 3 — "Image" is empty, and `MomentImage` is its sibling. |
| `MomentImage`       | prefixed | Rules 1 + 3, same pair.                                           |
| `CommitmentHistory` | prefixed | Rule 1 — "History" is empty.                                      |
| `RefreshToken`      | prefixed | Rules 1 + 3 — "Token" is empty; `AccessToken` is its sibling.     |
| `User`              | bare     | Root.                                                             |
| `UserAccount`       | prefixed | Rule 2 — "Account" is ambiguous (billing? tenant?).               |
| `UserVerification`  | prefixed | Rule 1 — "Verification" is too vague alone.                       |

Two costs of prefixing when no rule calls for it:

- **Prefixes compound down the tree.** Every level inherits all of its
  ancestors. The pre-rename `ActivityCaptureImage` was already three nouns, and
  a fourth level would have been unreadable. It is `MomentImage` now, not
  `ThreadMomentImage`, precisely to stop the accumulation.
- **A name that encodes a relation becomes a lie when the relation loosens.**
  Renaming a Go type is cheap; renaming a table, its columns, its queries, its
  mappers, and every DTO mirroring it is not. Relations loosen far more often
  than they tighten — a `Moment` created by photo backfill exists before it has
  any parent at all, which alone rules out `ThreadMoment`.

Entity names track `FEATURES.md`'s `Vocabulary` section, which is the
authoritative product vocabulary. When the two disagree, `FEATURES.md` wins and
the code follows.

## 4. Function Signature Conventions

- `ctx context.Context` is always the first parameter.
- `error` is always the last return value.
- More than 2–3 domain parameters on a usecase method → wrap them in an
  `<Operation>Input` struct instead of a long parameter list. (Compare
  `CreateThread(ctx, CreateThreadInput{...})` against `Login`/`Refresh`, which
  also take an `Input` struct despite having only 2–4 fields — consistency wins
  over "is this really necessary here.")
- Repository method signatures use plain Go types and `uuid.UUID` / `*entity.X`,
  **never** `db.*` (sqlc) or `pgtype.*` types. Those are translated at the
  mapper boundary and must not escape `internal/repository`.
- A repository method that needs both `id` and the requesting user's `userID`
  takes them as two explicit `uuid.UUID` params (not a struct) when there are
  only two — reserve `Input` structs for operations with optional/growing field
  sets (create/update/search), not simple lookups.

## 5. Interface Design: Prefer Shared Method Signatures Over Duplicated Implementations

Go satisfies interfaces **structurally**: a concrete method satisfies every
interface that declares a method with the _same name and signature_ — there's no
explicit `implements` declaration. This has a direct consequence for how you
design a new interface that needs a capability another interface already
exposes:

**Before adding a new interface, check whether an existing method already has
the exact signature you need.** If it does, name your new interface's method
identically, and let the existing concrete implementation satisfy both
interfaces — don't write a second method with different name but identical
logic.

```go
// GOOD — one implementation satisfies two interfaces because the
// method names match:
type ThreadRepository interface {
    GetByID(ctx context.Context, id, userID uuid.UUID) (*entity.Thread, error)
}
type ThreadAccessChecker interface {
    GetByID(ctx context.Context, id, userID uuid.UUID) (*entity.Thread, error)
}
// threadRepository.GetByID alone satisfies both — see:
var _ usecase.ThreadRepository = (*threadRepository)(nil)
var _ usecase.ThreadAccessChecker = (*threadRepository)(nil)
```

This isn't hypothetical — `internal/repository/thread_repository.go` used to
carry both `GetByID` and a copy-pasted `GetThreadByID` with identical bodies,
purely because `ThreadAccessChecker` had named its method differently. Renaming
it to match removed the duplicate outright (see PR #2). When you add a
compile-time assertion for a new interface, add both
`var _ Interface = (*impl)(nil)` lines next to each other so the intent ("this
one type deliberately satisfies two roles") is visible at a glance.

## 6. File Size Guidelines

- A `*_usecase.go` file stays as one file with the interface + all methods
  together up to **~5–6 methods or ~250–300 lines**. Past that, split per
  operation (`thread_usecase_create.go`, etc.) while keeping the interface
  declaration in the main file.
- A `*_dto.go` file stays one-file-per-entity (not per-operation) as long as it
  stays reasonable — don't preemptively split `CreateXRequest` /
  `UpdateXRequest` / `XResponse` into separate files.
- `router.go` stays a single flat file until the number of domains makes it
  unwieldy to scan; split into `<domain>_routes.go` only then.
- Small file size is not, by itself, a reason to merge two files that serve
  different concerns (see §2 on mappers) — the split exists to separate _reasons
  to change_, not to hit a line-count target.

## 7. Code Templates

### Entity (`internal/entity/<domain>.go`)

```go
package entity

import (
    "time"

    "github.com/google/uuid"
)

type Domain struct {
    ID        uuid.UUID
    UserID    uuid.UUID
    // ... plain Go fields only — no pgtype, no db.* types, no json tags
    // (json tags belong on the DTO, not the entity)
    CreatedAt time.Time
    UpdatedAt time.Time
    DeletedAt *time.Time // nil-able fields are pointers, not sentinel values
}
```

### Usecase (`internal/usecase/<domain>_usecase.go`)

```go
package usecase

import (
    "context"
    "fmt"

    "github.com/google/uuid"
    "github.com/ngodingvareng/memoria/internal/entity"
)

// DomainRepository — declared here (consumer side), implemented in
// internal/repository. Doc-comment any non-obvious not-found semantics
// per method (see §9).
type DomainRepository interface {
    Create(ctx context.Context, d *entity.Domain) (*entity.Domain, error)
    GetByID(ctx context.Context, id, userID uuid.UUID) (*entity.Domain, error)
}

type CreateDomainInput struct {
    UserID uuid.UUID
    Name   string
}

type DomainUsecase interface {
    CreateDomain(ctx context.Context, input CreateDomainInput) (*entity.Domain, error)
}

type domainUsecase struct {
    repo DomainRepository
}

func NewDomainUsecase(repo DomainRepository) DomainUsecase {
    return &domainUsecase{repo: repo}
}

// CreateDomain implements [DomainUsecase].
func (u *domainUsecase) CreateDomain(ctx context.Context, input CreateDomainInput) (*entity.Domain, error) {
    created, err := u.repo.Create(ctx, &entity.Domain{UserID: input.UserID, Name: input.Name})
    if err != nil {
        return nil, fmt.Errorf("creating domain: %w", err)
    }
    return created, nil
}
```

### Repository (`internal/repository/<domain>_repository.go`)

```go
package repository

import (
    "context"
    "errors"
    "fmt"

    "github.com/google/uuid"
    "github.com/jackc/pgx/v5"
    "github.com/jackc/pgx/v5/pgxpool"
    "github.com/ngodingvareng/memoria/internal/db"
    "github.com/ngodingvareng/memoria/internal/entity"
    "github.com/ngodingvareng/memoria/internal/errs"
    "github.com/ngodingvareng/memoria/internal/usecase"
)

var _ usecase.DomainRepository = (*domainRepository)(nil)

type domainRepository struct {
    q *db.Queries
}

func NewDomainRepository(pool *pgxpool.Pool) *domainRepository {
    return &domainRepository{q: db.New(pool)}
}

// GetByID implements [usecase.DomainRepository]. Returns errs.ErrNotFound
// if id/userID don't match any row (wrong owner, wrong id, or soft-deleted
// — indistinguishable from here, which is intentional, see §9).
func (r *domainRepository) GetByID(ctx context.Context, id, userID uuid.UUID) (*entity.Domain, error) {
    row, err := r.q.GetDomainByID(ctx, db.GetDomainByIDParams{ID: id, UserID: userID})
    if err != nil {
        if errors.Is(err, pgx.ErrNoRows) {
            return nil, errs.ErrNotFound
        }
        return nil, fmt.Errorf("get domain by id: %w", err)
    }
    return toEntityDomain(row), nil
}
```

### Mapper (`internal/repository/<domain>_mapper.go`)

import (

### Handler (`internal/delivery/rest/handler/<domain>_handler.go`)

```go
package handler

import (
    "log/slog"

    "github.com/go-playground/validator/v10"
    "github.com/gofiber/fiber/v3"
    "github.com/ngodingvareng/memoria/internal/delivery/rest/dto"
    "github.com/ngodingvareng/memoria/internal/delivery/rest/middleware"
    "github.com/ngodingvareng/memoria/internal/errs"
    "github.com/ngodingvareng/memoria/internal/usecase"
    "github.com/ngodingvareng/memoria/internal/validate"
)

type DomainHandler struct {
    usecase  usecase.DomainUsecase
    validate *validator.Validate
}

func NewDomainHandler(uc usecase.DomainUsecase) *DomainHandler {
    return &DomainHandler{usecase: uc, validate: validator.New()}
}

// CreateDomain godoc
// @Summary      Create a new domain
// @Tags         domains
// @Accept       json
// @Produce      json
// @Param        request body dto.CreateDomainRequest true "Create domain request"
// @Success      201 {object} dto.WebResponse[dto.DomainResponse]
// @Router       /domains [post]
func (h *DomainHandler) CreateDomain(c fiber.Ctx) error {
    var req dto.CreateDomainRequest
    if err := c.Bind().Body(&req); err != nil {
        return errs.ErrInvalidInput
    }
    if err := h.validate.Struct(req); err != nil {
        return &errs.ValidationError{Errors: validate.FormatValidationErrors(err)}
    }

    userID, ok := middleware.UserIDFromContext(c)
    if !ok {
        return errs.ErrUnauthorized
    }

    created, err := h.usecase.CreateDomain(c, usecase.CreateDomainInput{UserID: userID, Name: req.Name})
    if err != nil {
        return err
    }

    slog.InfoContext(c, "domain created", "domain_id", created.ID, "user_id", created.UserID)

    return c.Status(fiber.StatusCreated).JSON(dto.WebResponse[dto.DomainResponse]{
        Code:    fiber.StatusCreated,
        Message: "domain created",
        Data:    dto.NewDomainResponse(created),
    })
}
```

## 8. Comments & Documentation Style

- **Write comments for WHY, never WHAT.** Well-named identifiers already say
  what the code does. A comment earns its place only when it explains a hidden
  constraint, a subtle invariant, a workaround for a specific bug, or behavior
  that would surprise a reader (this mirrors the top-level project guidance and
  is enforced here specifically for `api/`).
- **English only, everywhere, no exceptions** — code, comments, docs, example
  strings. A single stray non-English comment
  (`// Login selalu memulai chain baru.`) made it into `auth_usecase.go` before
  being caught in review; don't let it happen again.
- **Never leave a scaffold/draft comment unresolved in committed code.** Phrases
  like _"if you like"_, _"log if needed, or ignore"_, _"assuming this is your
  util return type"_, or a NOTE addressed to a future reader as an instruction
  rather than documentation are a sign the decision was never actually made. Two
  real instances were found and removed from this codebase: a stale NOTE in
  `validate.ErrorResponse` referencing nonexistent `pkg/errs`/`pkg/util` paths,
  and a swallowed-error comment in `config.LoadConfig` that never decided
  whether a malformed `.env` should be visible. **Resolve the decision and
  delete the comment before merging — don't let "TODO for you" comments survive
  review.** If something is genuinely future work, it belongs in `TODO.md`, not
  as an inline comment implying the decision is still open in shipped code.
- Don't reference the current task, PR, or issue number in a comment ("fix for
  #123", "added for the X feature") — that context belongs in the commit message
  / PR description and rots as the code evolves.

## 9. Error Handling Standard

- **Reuse an existing `errs.Err*` sentinel before inventing a new one.** Check
  `internal/errs/app_error.go` first.
- **Sentinel identity matters — `errors.Is` is pointer-equality here.**
  `errs.AppError` has no `Is()` or `Unwrap()` method, so
  `errors.Is(err, errs.ErrNotFound)` only succeeds if `err` (or something it
  wraps via `%w`) is _literally_ the same `*AppError` pointer as the sentinel.
  This matters because several usecase/handler paths branch on it
  (`auth_usecase.go`'s Login/Refresh/Logout, `AuthHandler.Logout`'s
  idempotency). **Before adding a dynamic/parameterized error constructor**
  (e.g. one that formats a resource name + id into the message), check every
  `errors.Is` call site against the sentinel it's meant to stand in for — a
  dynamically-constructed instance will silently fail all of them unless it
  wires an `Unwrap()` back to the real sentinel. This exact mistake
  (`errs.NewResourceNotFoundError`) was caught as dead code before it could be
  adopted and cause exactly this bug — see PR #2.
- **Document not-found semantics per repository method** when it isn't the
  default. Two valid behaviors exist for a query that matches zero rows, and
  callers need to know which one they're getting:
  - Returns `errs.ErrNotFound` (default for `:one` sqlc queries via
    `errors.Is(err, pgx.ErrNoRows)`).
  - Silent no-op (for `:exec` sqlc queries with no rows-affected count — e.g.
    `SoftDelete`). Document this explicitly in a doc comment, and point callers
    at the `GetByID`-first pattern if they need a real 404.
- **Wrap once per layer crossing**:
  `fmt.Errorf("<lowercase action phrase>: %w", err)` when an error crosses from
  repository → usecase, or usecase → handler-visible. Don't re-wrap an error
  that's already been wrapped once within the same logical operation (e.g.
  inside a `WithTransaction` callback — the callback's own `Create`/`Update`
  call already wrapped it; returning it unwrapped from the callback avoids
  "creating thread: creating thread: insert thread: ..." stutter).
- **Log unexpected errors exactly once**, in `middleware.CustomErrorHandler` —
  this is the single point in the whole request lifecycle allowed to call
  `slog.ErrorContext` on an error. `usecase` and `repository` never log; they
  only return (optionally wrapped) errors and let them bubble up.
- **Log every successful mutation, never a successful read**, from the handler
  layer:
  `slog.InfoContext(c, "<domain> <verb, past tense>", "<domain>_id", id, "user_id", userID)`.
  Every `Create`/`Update`/`Delete` handler must have exactly one such line right
  before its success response. This was missed on
  `ThreadImageHandler.DeleteThreadImage` in a prior review pass — check new
  mutating endpoints against this.

## 10. Code Ordering Inside a File

1. `package` declaration.
2. Imports, `goimports`-grouped: stdlib, blank line, third-party, blank line,
   internal (`github.com/ngodingvareng/memoria/...`).
3. Package-level `const` (grouped in a `const (...)` block if more than one).
4. Compile-time interface assertions (`var _ Interface = (*impl)(nil)`),
   immediately after imports/consts, before the type they assert.
5. Interface declarations (repository interfaces before the usecase interface,
   in `usecase` files).
6. Input/Output structs.
7. The concrete struct + its `New<Type>` constructor.
8. Methods, **in the same order they're declared in the interface** — don't let
   implementation order drift from the interface's declared order; it's the
   first thing a reviewer scans to check completeness.

## 11. Testing Conventions

- Unit tests are gated behind `-tags=unit`; integration tests behind
  `-tags=integration` (the latter use `testcontainers-go` and need Docker). A
  plain `go test ./...` intentionally runs neither.
- Usecase unit tests mock repository interfaces via Mockery
  (`internal/usecase/mocks/`, `.EXPECT()` builder style) — never hit a real DB
  from a usecase test.
- Repository tests are integration tests against a real (containerized) Postgres
  — never mocked, since their entire job is verifying SQL behavior.
- After changing any interface listed in `.mockery.yaml`, run
  `just mock-generate` and commit the regenerated mock in the same PR — a stale
  mock that still compiles against an old method signature is worse than a
  missing one. (CI should eventually enforce this — see `TODO.md` Tier 4.)
- Test names: `Test<Type>_<Method>_<Scenario>` (e.g.
  `TestThreadUsecase_UpdateThread_NotFound`).

## 12. Pre-merge Self-review Checklist

- [ ] No two methods with identical logic implementing different interface names
      for the same capability — rename to share one method signature instead
      (§5).
- [ ] No unused exported function/type — `grep` its name across the repo before
      committing; if it has zero call sites, delete it rather than leaving it
      "for later."
- [ ] Any new child entity is named bare unless rule 1, 2, or 3 of §3.1 applies
      — a parent prefix added only to express "belongs to" duplicates what the
      foreign key already says.
- [ ] No leftover scaffold/draft comments ("if you like", "assuming this is...",
      a NOTE phrased as an instruction to a future dev) (§8).
- [ ] No non-English strings anywhere, including comments (§8).
- [ ] Every new mutating handler logs a success line; every new
      not-found-capable repository method documents its zero-match semantics in
      a doc comment (§9).
- [ ] Any new dynamic/parameterized `AppError` constructor has been checked
      against existing `errors.Is` call sites, or deliberately wires an
      `Unwrap()` back to the sentinel it's meant to represent (§9).
- [ ] New/changed interfaces have a matching regenerated mock
      (`just mock-generate`) committed in the same PR.
- [ ] File hasn't silently crossed the §6 size thresholds without a split plan.
- [ ] `go build ./...`, `go vet ./...`, and `go test -tags=unit ./...` all pass
      locally before pushing.
