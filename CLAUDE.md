# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Memoria — a private memory keeper built around capturing moments and history today so they can be revisited later. The core entity is the **Activity** (e.g. "Work," "Morning Run"), a recurring thread of a life, which can have many **Captures** — individual occurrences, either auto-generated on a fixed schedule (starting **open**, becoming **unrecorded** if the confirmation window passes) or added manually. Each Capture can carry a note, photos, a datetime, and a color. It's inspired by Instagram (social sharing) and GitHub's contribution heatmap (visualizing activity over time — including Settling Time, the gap between a moment happening and being recorded).

`FEATURES.md` is the full product spec and opens with **Principles** and **Non-Goals** that every feature is checked against — read those before proposing or implementing product behavior, since several are deliberate constraints that look like missing features (no streaks, no visible reaction counts, no read receipts, no real-time engagement notifications, and a hard firewall keeping fixed-schedule compliance data out of every archive surface). Beyond those it covers Activities, Captures, Circles (private social groups), Schedules, Notifications, Albums, Recaps, Looking Back surfaces, Lifecycle/deletion semantics, and Privacy controls. Note that `FEATURES.md` intentionally runs ahead of the code — treat it as the target, not a description of what exists, and check `api/TODO.md` for what is actually built.

This is a monorepo with four independent projects, each with its own toolchain and lifecycle:

- **`api/`** — Go backend (Fiber). The most mature and actively developed part of the stack.
- **`web/`** — React + TanStack Router frontend. Actively developed, currently UI-scaffolding stage (see below).
- **`mobile/`** — Flutter app. Early scaffold, not yet wired to the real API.
- **`ai/`** — FastAPI service intended to generate synopses from stories. Bare scaffold only.

There is no root-level build; always `cd` into the relevant project directory first.

## api/ (Go backend)

### Commands (run from `api/`)

```sh
make dev              # starts Postgres + RustFS via Docker, regenerates Swagger, runs the API (Ctrl+C tears Docker down too)
make dev-only         # run the Go app without touching Docker (DB/storage must already be up)
make build             # go build ./...
make test              # interactive prompt: unit, integration, or exits
make test-unit          # go test -tags=unit ./... -v
make test-integration   # go test -tags=integration ./... -v (needs Docker; uses testcontainers-go)
make db-generate        # wipes internal/db/*.go and regenerates from db/queries via sqlc
make migrate-create      # interactively scaffold a new golang-migrate file under db/migrations/
make mock-generate       # regenerates internal/usecase/mocks/ via Mockery (config: .mockery.yaml)
```

Run a single Go test: `go test -tags=unit ./internal/usecase/... -run TestActivityUsecase_Create -v` (swap the tag/path/pattern as needed; most tests are gated behind `-tags=unit` or `-tags=integration` build tags — a plain `go test ./...` will skip them).

First-time setup requires `cp .env.example .env` and installing `sqlc`, `golang-migrate`, `swag`, and `mockery` (see root `README.md` for exact install commands).

### Architecture

Clean architecture with a unit-of-work-flavored repository pattern (see https://rednafi.com/go/repo-txn-uow, referenced directly in the root README). Layers, dependency direction is strictly inward:

```
delivery/rest (handler, dto, middleware) → usecase → repository → db (sqlc-generated)
                                              ↓
                                           entity
```

- **`internal/entity/`** — plain domain structs, no framework/DB dependencies.
- **`internal/usecase/`** — business logic. Each usecase file defines its own narrow repository *interfaces* (e.g. `ActivityRepository` in `activity_usecase.go`) that the concrete `internal/repository/*` implementations satisfy — interfaces live on the consumer side, not next to the implementation. Mocks for these interfaces are generated by Mockery into `internal/usecase/mocks/` (see `.mockery.yaml` for the exact interface list — add new interfaces there before running `make mock-generate`).
- **`internal/repository/`** — implements the usecase-defined interfaces against `internal/db` (sqlc-generated queries). Each repository has a paired `*_mapper.go` (DB row ↔ entity conversion). Ownership checks (`WHERE ... AND user_id = ?`) are done inside repository queries, not as a separate authorization layer — see the comments in `activity_usecase.go` around `ActivityRepository.Update`/`SoftDelete`/`GetByID` for the exact semantics (silent no-op vs `errs.ErrNotFound`).
- **`internal/db/`** — 100% generated by `sqlc` from `db/queries/*.sql` + `db/migrations/*.sql` (see `sqlc.yaml`). Never hand-edit; run `make db-generate` instead. `uuid` columns are mapped to `google/uuid.UUID` (see the override in `sqlc.yaml`), not `pgtype.UUID`.
- **`internal/delivery/rest/`** — Fiber handlers, DTOs, and middleware. `router.go`'s `Handlers` struct and `SetupRoutes` is the single place new endpoints get registered; `internal/app/app.go`'s `NewContainer` is the single place dependencies get wired (repo → usecase → handler) and is the first place to look to understand how a new feature slots into the app.
- **`internal/errs/`** — centralized `AppError` (code + message) vocabulary; handlers/usecases return these and `middleware.CustomErrorHandler` translates them to HTTP responses. Prefer reusing an existing `Err*` sentinel over inventing a new one.
- **`internal/security/`** — JWT access tokens, refresh token generation, and scrypt password hashing, each behind a small interface consumed by `usecase` (`AccessTokenIssuer`, `RefreshTokenGenerator`, `PasswordHasher`).
- **`internal/storage/`** — `Storage` interface with an S3-compatible implementation (`s3_storage.go`), used against RustFS in dev. Swapping to MinIO/S3/R2 is a config change (`STORAGE_*` env vars), not a code change.
- Auth uses access + refresh JWTs; `RequireAuth` middleware (`internal/delivery/rest/middleware/auth_middleware.go`) populates the authenticated user id used for ownership checks throughout.
- Config is loaded from `.env` via Viper into a typed `Config` struct (`internal/config/config.go`) — add new env vars there with a `mapstructure` tag.
- Swagger docs are generated (`swag init`, wrapped by `make dev`'s `swagger-generate` step) into `docs/`, served at `/docs`.

`api/TODO.md` tracks in-flight and planned work in detail (auth refresh-token split, OAuth, scheduler/timeout workers, ownership-check gaps, etc.) — check it before assuming a feature is finished or unstarted.

CI (`.github/workflows/api-test.yaml`) runs `go test -tags=unit` then `-tags=integration` on every push/PR touching `api/**`.

### Architecture

- **Routing**: TanStack Router with file-based routes under `src/routes/`, auto-code-split. `src/routeTree.gen.ts` is generated — never hand-edit it (it's excluded from lint). Route groups use TanStack's `_layout` prefix convention: `_app.tsx`/`_app/` for the authenticated app shell, `_auth.tsx`/`_auth/` for sign-in/sign-up, `_user.tsx`/`_user/` for account settings pages, `_circle` for circle-scoped routes.
- **Features vs. components**: `src/features/<domain>/` (activities, album, auth, circles, mentions, notifications, users) holds domain-specific components, each re-exported through an `index.ts` barrel. `src/components/` holds cross-cutting/shared UI: `src/components/ui/` is the ShadCN-generated primitive library (`components.json` configures the ShadCN CLI) — treat these as generated/vendored and prefer composing over heavily editing them; `src/components/dialogs/` holds standalone dialog components used across features.
- **Styling**: Tailwind CSS v4 (via `@tailwindcss/vite`, no separate config file — see `src/index.css`), `class-variance-authority` + `tailwind-merge` for variant styling (`src/lib/utils.ts`'s `cn`), theme handled by `src/components/theme-provider.tsx`.
- **Forms**: TanStack Form + Zod.
- **Path alias**: `@/*` → `src/*` (configured in both `vite.config.ts` and `tsconfig.app.json` — keep both in sync if changed).
- **React Compiler** is enabled (via `babel-plugin-react-compiler` in `vite.config.ts`); avoid manual `useMemo`/`useCallback` micro-optimizations it already handles.
- No API client wiring exists yet — `src/lib/dummies.tsx` currently supplies placeholder/mock data for UI development.
- Linting is `oxlint` (not ESLint), configured in `.oxlintrc.json`; formatting is Prettier (`.prettierrc.json`).

## mobile/ (Flutter)

Early-stage scaffold, not yet integrated with the `api/` backend (`main.dart`'s app name/theme are still placeholder/starter values). Structure mirrors the web app's domain split: `lib/features/<domain>/` (activity, album, auth, circle, home, navigation, statistic) plus `lib/core/` for cross-cutting network (`core/network/api_client.dart`, `api_endpoints.dart`) and routing setup. Standard `flutter run` / `flutter test` workflow applies; no custom Makefile or scripts here.

## ai/ (FastAPI)

Bare FastAPI scaffold (`ai/main.py`) — intended purpose (per `ai/README.md`) is generating a synopsis from a large story/journal, but no such logic exists yet. Uses `uv` for dependency management (`pyproject.toml`, `uv.lock`, requires Python >=3.14). Run with `uv run fastapi dev main.py` or standard `uv run` invocations from `ai/`.

## Cross-cutting notes

- **All code, comments, docs, and UI/placeholder strings must be in English**, regardless of the language a request comes in. Generated artifacts (`api/docs/*`, `api/internal/db/*`) inherit their text from source (`db/queries/*.sql` comments, DTO `example` tags) — translate the source and regenerate (`swag init`, `sqlc generate`) rather than hand-editing generated output.
- The Go backend targets Linux specifically (some `Makefile` recipes use `bash -c` shell trap idioms); cross-platform support is a known gap, not an oversight.
- `api/AGENTS.md` contains one line: "always implement abstractions" — keep usecase-level repository/service interfaces even when there's currently only one implementation, per the existing pattern (interfaces defined by the consumer in `internal/usecase/*.go`, not colocated with the implementation).
